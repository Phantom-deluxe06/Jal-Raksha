# FloodSim-HADR (SIH26161)

AI-powered dam-break inundation modelling platform. See the PRD for full
scope. **Current status**: SWE simulation + 2D map + export (Build Priority
#1), an instant ML surrogate (#2), a 3D terrain view, and a localized SPH
solver with an SPH-vs-SWE comparison panel are all running end-to-end on
real data. GEE real-time SAR integration (#5) is in progress. Note: SPH/3D
were built in a separate work session on this repo — see git log for that
history; this README's SWE/ML sections below predate that work and haven't
been updated to cover it yet.

## Case study

2008 Kusaha embankment breach on the Kosi River (not the barrage itself —
see [data/README.md](data/README.md) for why). All input data is real,
programmatically fetched, cited: [data/dam_config/kosi_case_study.json](data/dam_config/kosi_case_study.json).

## Structure

```
data/           case-study DEM, population, satellite, breach config (see data/README.md)
scripts/        one-off data-fetch scripts (DEM, population, satellite)
backend/
  swe/          the SWE solver (solver.py, dem_utils.py, colorize.py) + run_kosi_swe.py orchestrator
  outputs/      generated simulation results (gitignore-worthy, regenerated by running the solver)
  main.py       FastAPI app serving simulation results + exports
frontend/       React + Vite + react-leaflet map/timeline UI
.venv/          Python venv (rasterio, geopandas, fastapi, ...)
```

## Running it

**Backend** (from repo root):
```
.venv\Scripts\python.exe -m uvicorn backend.main:app --port 8000
```
First request to `/simulate/result/kosi_actual2008` needs a run to exist —
either run the solver directly once:
```
.venv\Scripts\python.exe backend\swe\run_kosi_swe.py
```
or `POST /simulate/swe` (same thing, via the API — this is what the
frontend's "Re-run simulation" button calls). A run takes ~2 minutes.

**Frontend**:
```
cd frontend
npm run dev
```
Open http://localhost:5173 (backend must already be running on :8000 — CORS
is open for local dev).

> **The backend does NOT auto-reload on code changes.** `uvicorn` here is
> started without `--reload`, so after editing `backend/main.py` or any
> module it imports (`backend/swe/`, `backend/ml/`, `backend/sph/`), the
> running server keeps serving the old code silently — a new/changed route
> can 404 or misbehave with no error pointing at the real cause. After any
> backend edit: find and kill the old process, then start a fresh one.
> ```
> Get-CimInstance Win32_Process -Filter "CommandLine LIKE '%uvicorn%'" | Select-Object ProcessId
> Stop-Process -Id <that PID> -Force
> Start-Process -FilePath ".venv\Scripts\python.exe" -ArgumentList "-m","uvicorn","backend.main:app","--host","127.0.0.1","--port","8000" -WorkingDirectory "<repo root>" -WindowStyle Hidden
> ```
> The server also isn't kept running between work sessions — check
> `curl http://127.0.0.1:8000/health` before assuming it's up.

## What the SWE stage does

- Loads the real 30m SRTM DEM, downsamples to ~185m for solver tractability
- Runs a from-scratch 2D shallow-water-equations solver (explicit
  Lax-Friedrichs finite-volume, Manning friction, wetting/drying) seeded with
  the **actual documented 2008 breach discharge (3,675 m³/s)**, not the
  barrage's theoretical design discharge (27,000 m³/s) — see
  `backend/swe/run_kosi_swe.py` and the `dam_config` JSON for why that
  distinction matters and is always labeled explicitly in the output
- Outputs a 17-frame time series (0–4h, 15min steps) of depth grids as
  GeoTIFF + colorized PNG overlays + per-frame GeoJSON flood polygons
- Runs sanity checks every time (mass conservation, non-trivial/non-saturated
  extent, solver stability) and an explicit, clearly-labeled comparison
  against the historical ~3,700 km² figure — flagged as context-only since
  the AOI is intentionally smaller than the full historical extent
- Serves it all through FastAPI and renders it in a Leaflet map with a
  scrubbable timeline and GeoJSON/Shapefile/KML export

Every number in `backend/outputs/swe_kosi_actual2008/metadata.json` comes
from actually running the solver on the real DEM + real breach config — none
of it is hardcoded or estimated. All modeling assumptions (Manning's n,
breach hydrograph shape, grid resolution, open boundaries) are listed in that
file's `assumptions` array and surfaced in the frontend's "Modeling
assumptions" panel, not buried.

## ML surrogate (Build Priority #2)

- **Training data** (`backend/ml/generate_training_data.py`): 60 real SWE
  solver runs (48 train / 12 held-out validation) at ~300m resolution
  (coarser than the 185m "Full SWE" grid, for training-data throughput),
  each with randomly sampled discharge (50-150% of the actual 3675 cumecs,
  matching `dam_config.simulation_defaults.volume_override_range_pct`) and
  breach location (±6 grid cells / ~1.8km jitter around the documented
  breach site). All 60 runs were stable; none discarded. Took 22 min.
  Manifest with every sample's exact parameters: `backend/ml_data/manifest.json`.
- **Model** (`backend/ml/model.py`): a ~1.1M-parameter 3-level U-Net (input:
  normalized elevation + breach-distance field + discharge field, output:
  predicted depth grid). Trained 200 epochs in 2.4 min on the RTX 4060.
- **Validation** (`backend/ml_checkpoints/training_report.json`): mean IoU
  0.894 (min 0.832) and mean depth RMSE 0.006m across all 12 held-out runs
  — reported per-sample, not just averaged, so no weak case is hidden. This
  is a small dataset for a from-scratch CNN; the caveats array in that file
  explains why accuracy is expected to degrade outside the sampled ranges.
- **Endpoint**: `POST /predict/instant` (warmed at server startup so even
  the first request is fast) — server-side inference is ~30-40ms, well
  under the <2-3s budget.
- **Frontend**: a "Full SWE Simulation" / "Instant AI Prediction" toggle;
  the instant mode exposes discharge and breach-location sliders and shows
  its own grid resolution so it's clear the two modes aren't pixel-for-pixel
  comparable (different grid, see above).

## Digital Twin sync (Kosi Barrage CWC gauge)

- **Real source, found by investigation, not assumed**: the Central Water
  Commission's public Flood Forecasting System (`ffs.india-water.gov.in`) is
  an Angular dashboard backed by an undocumented but unauthenticated JSON
  API. Its station `062-MGD4PTN` ("KOSI BARRAGE", type Inflow) matches our
  case study's barrage coordinates. See `backend/digital_twin/cwc_client.py`.
- **Cadence is measured, not assumed**: `sync.py` pulls 14 days of history
  and computes the median interval between readings every sync — currently
  ~24h (one reading/day, ~08:00 IST). Two other datatypes this station
  reports (FIN, FOL) were found stale (last updated 2021) during
  investigation and are explicitly excluded from "current state", not
  silently shown as live.
- **Never fabricates on failure**: a failed sync leaves the last
  successfully-synced state untouched and logs the failure (`sync_log` in
  `backend/outputs/digital_twin/state.json`) rather than overwriting good
  data with an error or a stale guess.
- Background poll (hourly, since the source itself is daily — see
  `main.py`) + `POST /twin/sync` for an on-demand pull + `GET /twin/state`.
  Frontend: a "Live Twin" tab, separate from the simulation modes, showing
  both the CWC reading timestamp and this app's own last-sync timestamp
  side by side, plus a gauge against FRL/MWL reference levels.
